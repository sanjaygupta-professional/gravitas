gravitas explained simply

A small gravity simulation whose parallel parts are mathematically proved correct by the compiler.

1. The one-minute version

What it does: simulates 1,024 bodies pulling on each other with gravity (a heavy one in the middle, a cloud of light ones around it), for 100 time steps, using all your CPU cores at once.

What's unusual: the physics isn't the point. Splitting work across cores is a classic place for silent bugs: a chunk of work gets dropped, counted twice, or mass appears from nowhere. Here, the rules that must never break are written down as laws, and the compiler proves the code obeys them. If someone edits the code so a law breaks, the proof step fails.

What it's written in: Bend 2, a language that runs on many cores automatically and can check proofs. There is no AI agent or server inside the project. It's 4 source files and a compiled binary. (An AI may well have helped write the code, but nothing AI-related runs when you use it.)

2. The big idea two halves, treated differently

PROVED

The shape

How many bodies exist, how much total mass there is, and how the parallel forks recombine. Exact whole-number arithmetic (Nat), so a proof is possible.

CHECKED AT RUNTIME

The numerics

The actual gravity maths, done in decimals (F32). Bend can't prove things about floating point, so sim.bend just asserts count and mass at the end and crashes loudly if they changed.

3. Architecture the four files and who uses whom

Plus bend: a tiny shell script that runs the Bend compiler and trims its very long error messages.

4. How the parallelism works a tree of forks

The 1,024 bodies sit in a balanced binary tree (210 leaves). Every node in the tree is a fork; every leaf is one body. Bend hands the two branches of each fork to different cores automatically. You never write a thread or a lock.

The one line that does it: a b = field(p, x, …) field(p, y, …), meaning "compute both, at the same time".

5. What happens in one simulation step

Every body is compared with every other body (O(N²) = about a million pairs per step). That is the simple, expensive way, which is why the parallelism matters.

7. The safety gate the reason this project exists

Worked example from the README. Change fusion to keep only the first body's mass (Nat.add(m1, m2) → Nat.add(m1, 0n)):

normal type check
$ bend main.bend --check-only
All terms check.

Perfectly valid code, so an ordinary compiler is happy.

the gate
$ bend PROOF.bend
Error:
- expected : Nat.add(m1, 0n)
- observed : Nat.add(m1, m2)
Location: LAWS.zip_mass

Rejected. Mass would silently vanish.

Why this matters for AI-written code: you review the 8 laws once. After that an agent can rewrite main.bend freely and the proof step rejects anything that breaks a rule.

8. The eight laws in plain English

LawIn plain wordsWhy you'd care
count_pow2Depth d always means exactly 2d bodies.No body lost in the tree walk
accels_countUpdating bodies never changes how many there are.The building block for the next one
step_countA full simulation step never adds or drops a body.The headline guarantee
field_splitPull from two halves = pull from left + pull from right.Forking gives the same answer as not forking
comsum_splitSame, for the centre-of-mass calculation.Same
zip_countMerging two systems keeps the size.Safe merging of runs
zip_massMerging carries exactly the combined mass.No mass invented or lost (the hardest proof)
zip_swapMerging A into B equals merging B into A.Order doesn't matter

10. What is not proved honest limits

  • The gravity itself. Decimal (F32) maths can't be proved in Bend, so physical accuracy is not guaranteed.
  • Total mass staying constant during a step. True and checked while the sim runs, but the current proof tool can't get at a mass stored inside a body record. The README suggests a refactor (a parallel tree of bare numbers) that would make it provable.
  • The "cloud" is really 10 distinct light bodies stacked in copies (10, 45, 120, 210, 252, …), because spawn derives seeds from the path down the tree rather than from the body's index. Found by running it; details in run-visual.html. The proofs don't cover this.
  • The centre of mass drifts slightly (0.233,1.040) → (0.264,1.094). That's rounding from summing in different orders, not a bug. It's also a useful alarm: it would move noticeably if a fork were wrong.
  • Small inconsistencies in the repo: main.bend's header mentions a check.bend that doesn't exist (the checks are in sim.bend), and sim.bend prints "law step_mass" though there is no such law in LAWS.bend. Both are cosmetic.
